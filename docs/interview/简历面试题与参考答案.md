# 分布式 KV 项目面试题与参考答案

> 本文根据项目当前代码和简历描述整理。回答中明确区分“当前已实现”和“后续设计”，避免把设想说成已交付能力。面试时应按自己的实际贡献调整“我负责”的表述。

## 一、项目整体与个人贡献

### 1. 请用三分钟介绍项目，一次 Put 请求经过哪些组件？

**参考回答：**

这是一个 C++17 分布式 KV 系统，客户端通过 `db + table + key` 访问数据。Catalog 管理库表元数据和 DDL；Topo 管理 Storage 节点、分片副本组和路由；Storage 为每个分片运行 Raft 复制组，并用 WAL、Snapshot 和状态机恢复数据；SDK 缓存路由、计算 Key 对应的 shard，并处理错误分类、路由刷新和重试。

一次 Put 大致经过：SDK 从路由缓存取得表路由，使用稳定哈希计算 shard，向该 shard 的 Leader 发 RPC；Leader 将写请求作为 Raft 日志提议，持久化并复制给 Voter 多数派，确认提交后返回；已提交日志随后应用到 KV 状态机。客户端超时导致结果无法确认时，SDK 在预算内重试同一个 `request_id`，最终仍不确定则返回 `UNKNOWN`。

当前边界包括：KV 运行时引擎是内存 Map、建表后 shard 数固定、Catalog 和 Topo 是单进程，尚无在线 split 和动态 rebalance。

### 2. 你写了“从零实现”，哪些是自己实现的？哪些用了第三方库？

**参考回答：**

我会按真实贡献逐项说明，不能把整个仓库所有模块都笼统说成个人独立完成。项目的分布式核心包括自有的 Raft Core、日志复制与成员管理、Storage/Topo/Catalog 服务、SDK 路由与重试、WAL/Snapshot 和测试链路；工程基础设施使用 C++17 及项目依赖的 gRPC、Protobuf、fmt、spdlog 等库。

如果面试官追问某个具体模块，我会进一步讲清自己负责的代码入口、关键状态转换、失败处理和对应测试。第三方库提供 RPC、序列化或日志等基础能力，不代表共识与状态机逻辑由库代做。

### 3. Catalog 和 Topo 为什么拆开？如何避免职责重叠？

**参考回答：**

Catalog 面向逻辑库表和 DDL：保存表规格及期望生命周期，并推进建表、改副本数和删表。Topo 面向物理拓扑：维护节点、每个 shard 的 ReplicaGroup、实际副本观测和可发布路由。Catalog 的表规格是上层意图，Topo 将意图落实为节点上的副本。

跨组件操作按持久状态和后台 reconcile 推进，而不是依赖单个跨进程同步调用原子完成。Catalog 会记录 DDL 状态，Topo 根据目标规格持续收敛；状态查询再决定 Catalog 是否结束操作。这样能处理 RPC 失败和进程重启，但 Catalog 和 Topo 当前各自是单进程，控制面尚未高可用。

### 4. Storage 节点、分片、副本和 Raft 组是什么关系？

**参考回答：**

表被划分为多个 shard；每个 shard 有若干副本，这些副本组成该 shard 独立的 Raft 组。一个 Storage 进程/节点可以承载多个不同 shard 的副本，因此节点故障可能同时影响多个 Raft 组。每个组有自己的成员、Leader、日志和多数派，不能把整个 Storage 集群理解成一个 Raft 组。

### 5. 项目最明显的限制是什么？生产化会先补什么？

**参考回答：**

当前明确限制包括：KV 数据运行在内存 Map，WAL 和 Snapshot 用于恢复但不是成熟的磁盘 KV 引擎；分片数建表时固定，没有在线 split 和动态 rebalance；Catalog 与 Topo 是单进程；`request_id` 记录当前没有 TTL；坏副本替换后原副本恢复时的处理策略仍可改进。

生产化我会先根据目标 SLA 补控制面高可用、备份与恢复演练、在线迁移方案、去重记录生命周期和运维可观测性，并补足故障注入和容量测试。优先级需要由业务的数据丢失目标、恢复时间目标和部署故障域决定。

## 二、稳定哈希、分片与 Reconcile

### 6. 为什么选 FNV-1a 64 位？为什么不直接用 `std::hash`？SDK 和 Topo 如何保持一致？

**参考回答：**

项目选用固定实现的 FNV-1a 64 位作为轻量、确定性的路由哈希。`std::hash` 的标准不承诺结果跨实现或跨版本稳定，不适合作为持久路由协议的一部分。SDK 与 Topo 共用 `stable_shard_index()`，按 `hash(key) % shard_count` 计算 shard；`table_id` 不参与 Key 哈希。

分片数改变会改变取模结果，所以不能只修改 shard 数后直接上线，必须迁移数据并协调路由切换。当前项目不支持在线 split 或动态 rebalance。

### 7. 分片数和副本数有什么区别？加节点、加副本、加分片分别解决什么问题？

**参考回答：**

分片数决定数据被分成多少个独立 Raft 组，影响 Key 的分布和并行度；副本数决定每个 shard 有多少 Raft 成员，影响数据冗余和故障容忍度。增加 Storage 节点只是增加可调度资源；增加副本数会把副本放到更多节点；增加分片数则改变 Key 到数据组的划分。

当前项目支持通过 `AlterTableReplicaCount` 调整副本数，也能把新增 Storage 节点作为候选资源；不支持改变既有表的 shard 数。单个热点 Key 仍固定落到一个 shard，仅增加副本通常不能分散该 Key 的写入。

### 8. 为什么采用期望状态和后台 Reconcile，而不是建表 RPC 同步创建所有副本？RPC 返回成功代表什么？

**参考回答：**

建表涉及多个进程、多个节点和 Raft 成员变更，耗时且任一阶段都可能失败。若把所有动作塞进一个同步 RPC，就难以在客户端超时、网络故障或进程重启后可靠续跑。项目先持久化期望状态，再由后台 Reconcile 反复比较目标与实际状态，推进副本创建、追赶、成员变更和路由发布。

因此 DDL RPC 成功表示请求被接受或期望状态已记录，不必然意味着所有副本已 READY、成为 Voter 且路由可写。需要观察最终 Table/Replica/Route 状态。

### 9. 建表下发到 Storage 后 Topo 崩溃，会不会重复创建副本？如何幂等？

**参考回答：**

分布式流程不能依赖“请求只执行一次”。控制面重启后从持久化的期望状态继续 reconcile；重复的创建/心跳指令需要以稳定的 table、shard、replica 标识识别同一个逻辑对象，并让 Storage 操作可重复执行。Catalog DDL 也使用 `operation_id` 处理同一操作的幂等重试。

面试时我会说明本项目实际依赖的对象 ID、状态检查和幂等入口，并区分“重复发命令”与“创建重复副本”。如果需要增强保证，可以对操作阶段和结果持久化，并测试每个持久化边界处的崩溃恢复。

### 10. 坏副本替换如何进行？为什么先 Learner，何时升为 Voter？

**参考回答：**

Topo 发现目标副本 LOST 或 ERROR 后，先选择空闲节点创建替代副本。现有 Leader 通过配置日志将其加入为 Learner；Learner 不参与投票多数派，先通过日志复制或 Snapshot 追赶。当前实现会在 Learner 的 match index 追到 Leader 的日志末尾后提议 PROMOTE_VOTER。之后再按成员变更流程移除坏成员。

先追赶再成为 Voter，可以避免一个数据明显落后的新成员增加投票集合并影响共识安全。整个流程依赖现有 Raft 组还能工作；失去多数派时，普通成员变更无法保证推进。

### 11. 如何区分节点崩溃和心跳暂时超时？原副本恢复会怎样？

**参考回答：**

Topo 依据心跳时间先把节点标为 SUSPECT，超过离线阈值后才标为 OFFLINE；副本状态是根据期望状态、节点状态和 Storage 上报的观测事实投影出来的。这样把原始观测与控制面决策分开，避免一次心跳延迟立刻等同于数据丢失。

节点恢复后，LOST 副本可重新进入创建/恢复流程。但如果替代副本已成为 Voter，当前仓库文档指出“原坏副本恢复时可能把新副本踢掉”的策略仍需优化，不能声称已解决所有并发恢复情形。

### 12. 并发后台任务怎样避免重复补副本或误删？

**参考回答：**

项目通过单一业务 owner 维护关键状态字段，并在写事务中重新读取当前 ReplicaGroup 和 Replica 状态后再更新目标成员，避免直接使用很早以前的快照做决定。操作还要保持幂等，并通过 mode 和成员状态约束当前允许推进的阶段。Table 外部 DDL 的并发也有明确约束。

如果进一步增强，我会为操作加入版本/CAS 条件、对同一 shard 的配置变更串行化，并为每个 reconcile 阶段增加重启和并发测试。具体回答要对齐代码里真正使用的锁、事务和状态约束，不泛称“有锁所以安全”。

## 三、Raft 选举、复制与成员变更

### 13. Leader 崩溃后如何选举？高 `currentTerm` 和更新日志有什么区别？

**参考回答：**

Follower 超时后先发起 PreVote，获得多数派预投票后才进入正式 Candidate，增加 term 并发送 RequestVote。投票节点检查候选者日志是否至少和自己的日志一样新，并且每个 term 只给符合条件的候选者投票；候选者取得 Voter 多数票后成为 Leader。

`currentTerm` 是节点当前观察到的选举任期，不表示数据完整度。日志新旧比较候选者最后日志的 `lastLogTerm`，term 相同再比较 `lastLogIndex`。一个隔离节点可以有更高 currentTerm，但仍持有落后日志，因此不能仅凭 term 当选。

### 14. 为什么要 PreVote？

**参考回答：**

网络分区中的少数派节点收不到心跳，可能反复提高 term 并发起正式选举。恢复连接后，健康节点看到更高 term 会退回 Follower；但该旧节点仍可能因拿不到多数票或日志落后而无法当选，导致健康集群被无谓打断。

PreVote 在正式提高 term 前先探测多数派是否会支持候选者。隔离节点拿不到多数 PreVote，就不进入正式选举，不会用失败选举持续抬高 term。它不让少数派写入，也不能替代正式投票或恢复丢失的数据。

### 15. Leader 收到写入后，何时可以返回成功？WAL、commit 和 apply 分别是什么？

**参考回答：**

WAL 持久化表示本地日志在故障恢复时有持久记录；日志复制到 Voter 多数派并满足 Raft 提交规则后，才是 commit；状态机 apply 是把已提交日志执行到 KV Map。三者不是同一时刻，也不能把“本地写入 WAL”当成客户端写成功。

当前 Put 等待提案提交后可返回 OK，状态机 apply 可以由后台任务随后完成。线性一致 Get 会在读取前确认 ReadIndex，并确保状态机 apply 到读位置。

### 16. 为什么旧任期日志复制到多数派仍不一定能直接提交？新 Leader 的 no-op 有什么用？

**参考回答：**

Raft 的提交推进对当前任期日志有特殊约束：Leader 不能只看到某条旧 term 日志复制到了多数派，就直接把它当作已提交。否则在特定后续选举中，可能破坏已提交前缀的安全性。新 Leader 先追加当前 term 的日志并使其提交后，可以据 Raft 规则安全推进之前的日志前缀。

项目在成为 Leader 后追加 no-op。它也为 ReadIndex 提供条件：当前任期已有已提交 entry 后，Leader 才能安全使用当前 commit index 处理线性一致读。

### 17. Follower 日志冲突怎样修复？哪些日志可以截断？

**参考回答：**

Leader 在 AppendEntries 中发送前缀位置的 index/term。Follower 校验本地对应日志；不匹配就拒绝，Leader 回退 next index 后重试。找到冲突的未提交后缀后，Follower 可以截断冲突后缀并追加 Leader 日志；已提交日志不能被静默覆盖。

如果 Follower 已落后于 Leader 当前保留的日志，Leader 会通过 Snapshot 安装恢复到快照边界，再复制其后的日志。落后副本必须继续追赶，安装完成不等于已追到最新。

### 18. 三副本扩成四副本时，多数派如何保持安全？是否实现 Joint Consensus？

**参考回答：**

当前实现把新副本先作为 Learner 加入，追到 Leader 日志后再提升为 Voter，并将配置变更写入 Raft 日志；同一时间限制未完成的配置变更，Topo 按加入、追赶、升 Voter、移除旧成员推进。Learner 不计入 quorum。

我不会把当前实现描述成完整的 Joint Consensus。源码采用 ADD_LEARNER、PROMOTE_VOTER、REMOVE_MEMBER 这些配置操作；如果问题要求标准 Raft 配置变更的完整证明，我会说明需要逐条核对项目对成员数变化时 quorum 的处理，不能仅凭“配置写入日志”声称实现了 joint configuration。生产级改进可采用经过严格验证的联合配置协议，或限制为能证明安全的成员变更路径，并覆盖多数派变化与故障交错测试。

### 19. 三副本坏两个后为什么不能直接加两个空副本？全组崩溃和磁盘丢失有何不同？

**参考回答：**

三副本需要两个 Voter 构成多数派。只剩一个时，不能正常提交写入，也不能依赖普通 Raft 成员变更把两个空节点变成原数据的合法副本。空节点没有日志和状态机数据，Topo 的目标副本数不能替代共识证明或数据恢复。

如果只是所有进程停止但原磁盘 WAL/Snapshot 完好，重启原副本后可能恢复；有足够原 Voter 互通即可重新选举。若所有副本持久化数据永久丢失，则需要备份恢复，Raft 本身无法凭空重建数据。当前项目未实现整个组永久丢失后的自动灾备接管。

## 四、ReadIndex 与线性一致读

### 20. 为什么 Leader 不能直接读取本地 Map？网络分区中的旧 Leader 有什么风险？

**参考回答：**

节点可能因网络分区失去多数派，却仍在本地认为自己是 Leader。若它只读本地 Map，就可能返回旧数据，甚至在新 Leader 已提交新写后继续向客户端提供过期结果。

项目的 Leader 读通过 ReadIndex 确认当前任期已有已提交日志，并和多数派确认 Leader 身份；之后等待本地状态机 apply 至安全读索引再读 Map。失去多数派时读失败，而不是退化为不声明的陈旧读。

### 21. ReadIndex 流程是什么？为什么既要 quorum，又要 apply 到 read index？

**参考回答：**

Raft Core 首先确认本任期已有已提交 entry，并将当前 `commit_index` 作为 read index；Leader 向 Voter 广播 AppendEntries/心跳，检查是否有多数派仍以当前 term 响应，以确认自己仍是有效 Leader。随后 Replica 将已提交日志 apply 到状态机，并确认 `apply_index >= read_index`，再读取 Map。

quorum 确认解决“当前是否仍是 Leader”；apply 检查解决“本地状态机是否已经包含 read index 之前的已提交写”。只做其中一个都不够。

### 22. 为什么新 Leader 要先提交当前任期日志才能处理安全 ReadIndex？

**参考回答：**

新 Leader 刚当选时，可能继承旧 term 的日志，但尚未建立当前任期的提交位置。没有当前任期已提交 entry 时，仅用当前 commit index 做 ReadIndex 可能无法证明此前日志提交状态已安全确定。

项目当选后追加 no-op；`build_append_entries_for_read()` 检查当前任期已有已提交 entry 后，才返回 read index。若条件未满足，读会得到 `READ_INDEX_NOT_READY`，SDK 可按策略重试。

### 23. ReadIndex 确认后、读 Map 前发生切主，还能线性一致吗？线性化点是什么？

**参考回答：**

ReadIndex 的核心是：本次读取在某个时刻取得了有效多数派确认，并且状态机推进到该确认对应的提交位置。请求随后读取不早于该位置的状态，因此能将读取线性化在确认之后、返回之前的区间内。新 Leader 不能丢弃已经提交的日志前缀。

如果并发写发生在 ReadIndex 建立后，它是否必须被本次读观察到取决于其提交与读操作的先后关系；不能笼统说“ReadIndex 后所有并发写都可见”。具体边界要按请求重叠关系和提交位置解释。多数派确认失败或状态机追赶失败时，项目返回错误，不返回未经验证的数据。

### 24. ReadIndex 和 Lease Read 有什么区别？为什么选 ReadIndex？多数派不可达时 Get 如何处理？

**参考回答：**

ReadIndex 对读请求进行多数派确认，再读取已 apply 的状态；代价是读延迟和可用性受 quorum RPC 影响。Lease Read 在一个有效租约期内允许 Leader 本地读，可能降低读延迟，但安全性依赖时钟漂移、暂停和租约边界等假设。

项目实现 ReadIndex，没有实现 Lease Read。多数派不可达时不能确认 Leader 身份，Get 返回错误；SDK 在预算范围内重试，最终仍不满足读条件则返回可重试/失败状态，而不是声称始终可读。

## 五、SDK 重试、request_id 与 UNKNOWN

### 25. 哪些错误刷新路由？哪些重试？为什么不能无条件重试？

**参考回答：**

SDK 按错误分类处理。`NOT_LEADER`、`REPLICA_NOT_FOUND`、`ROUTE_NOT_FOUND`、`IS_RECOVERING` 和 `RPC_ERROR` 会触发路由刷新并重试；`NOT_YET_COMMIT`、`READ_INDEX_NOT_READY`、`RESOURCE_EXHAUSTED` 可重试但不一定刷新路由。参数错误等不可重试错误直接返回。

无条件重试会放大负载、延迟失败请求，并可能重复执行有副作用的操作。对于结果不确定的写操作，必须使用相同 request_id，并受次数和总 deadline 限制。

### 26. 总超时怎样分配给路由刷新、Storage RPC 和退避？

**参考回答：**

每个逻辑请求先建立总 deadline。每次 Topo 或 Storage RPC 的 timeout 取 `min(rpc_timeout, deadline 剩余时间)`；路由刷新也消耗同一预算。重试间隔从配置值开始逐次翻倍，但睡眠不超过剩余时间。Storage 尝试次数和路由刷新次数分别受各自预算限制。

这样单次 RPC、刷新和退避不会各自重新获得完整总超时。如果每一步都独立使用完整超时，多个重试可能让一次调用远超业务方给定的时限。

### 27. 写已提交但响应丢失，重试怎样去重？同 ID 不同内容怎么办？

**参考回答：**

服务端状态机维护已 apply 的 request record，记录 request_id、操作类型和请求 payload hash。重试请求到达后，服务端查记录：相同 ID 且操作和内容匹配时不再执行写入并返回成功；同一个 ID 被用于不同操作或 payload 时返回参数冲突错误。

如果原请求仍在 inflight 阶段，ReplicaLoop 也会合并同一请求的等待者，避免同一进程内重复提议。SDK 的同一逻辑写在每次重试中复用同一个 request_id。

这提供有边界的幂等重试语义，不等于跨任意系统的 exactly-once；当前 request record 没有 TTL，长期积累需要后续生命周期设计。

### 28. request record 何时写入？KV 和去重记录如何保持一致？

**参考回答：**

写请求和 request_id 一起进入 Raft 日志；只有日志被 apply 到确定性状态机时，才更新 KV 并登记对应 request record。两者在同一次状态机 apply 中按固定顺序处理，Snapshot 捕获 KV、request records 与 apply index/term 的同一状态机视图。崩溃恢复时从该快照恢复，再按后续日志重放。

必须特别区分“日志已提交”和“状态机已 apply”：客户端可以在提交后收到成功，而 apply 由后台推进；重启恢复需要重放已提交日志使 KV 与去重记录重新一致。项目当前是内存 Map 加 WAL/Snapshot，并非 KV 与记录分别写入两个独立存储后再做分布式事务。

### 29. 为什么返回 UNKNOWN？客户端收到后怎么办？Get 能准确判断原请求是否成功吗？

**参考回答：**

RPC 超时可能发生在服务器提交前，也可能发生在提交后响应返回前。客户端无法仅凭超时判定写一定成功或失败，因此 SDK 在曾出现提交不确定性且预算耗尽时返回 `UNKNOWN`。

调用方应保留原 request_id，并用相同 ID 重试，让服务端查询去重记录。随后 Get 可以作为业务层检查，但它不一定能准确证明原请求的提交结果，例如值可能被后续写覆盖，Delete 后 Key 不存在也不能说明哪次操作产生了该状态。

### 30. 项目是 exactly-once 吗？去重记录无 TTL 有什么问题？加 TTL 又有什么边界？

**参考回答：**

我会称它为带 request_id 的幂等重试/去重机制，不会笼统宣称端到端 exactly-once。记录可以识别已经 apply 的重复写，并在 Snapshot/恢复后保留；但调用方必须稳定复用 ID，记录保留范围有限，且不覆盖外部副作用或跨 shard 原子事务。

当前没有 TTL，记录会随请求增长，增加内存、Snapshot 和恢复成本。增加 TTL 后，超过保留期限的旧请求 ID 可能再次被当作新请求，因此需要定义保留窗口、客户端最大重试期限和清理规则，并在 Snapshot/恢复及重复请求语义中保持一致。

## 六、WAL、Snapshot 与测试

### 31. 重启时如何区分已提交日志和仅追加未提交日志？能否把 WAL 全部 apply？

**参考回答：**

WAL 表示本地持久化的 Raft 日志，不单独证明每条日志都已提交。状态机只能 apply 已提交日志；恢复时还需要恢复 Raft 元数据、成员配置和快照边界，再由 Raft 恢复流程推进 commit/apply。不能把 WAL 中所有日志都直接应用，否则可能把曾经只存在于故障 Leader 上、后来被新 Leader 覆盖的未提交日志当成业务成功。

面试中我会沿着项目的 RecoverResult、快照 index、WAL entries 和 Raft 恢复状态说明实际边界；若被问到“崩溃时 commit index 是否独立持久化”，应按代码回答，不把通用 Raft 理论误当成项目实现细节。

### 32. WAL 写一半崩溃如何识别？损坏可能涉及已提交数据时能否截断？

**参考回答：**

项目用 framed record 编码 WAL，读取时检查记录完整性、解码结果和日志 index 连续性；遇到部分记录或解码错误会标记恢复问题。恢复还会将 Snapshot 覆盖范围内的日志过滤掉，并检查 Snapshot 之后的 WAL 是否从 `snapshot_index + 1` 连续开始。

发现损坏不等于可以安全丢弃。如果损坏记录可能是已提交日志，单机 WAL 无法证明其未提交；应通过健康副本的 Raft 日志或 Snapshot 恢复，必要时将副本置于恢复/故障状态，而不是宣称静默截尾一定安全。项目的 WAL 恢复路径会标记 need_recover，具体处置应按当前实现描述。

### 33. Snapshot 保存什么？如何保证数据和 index/term 一致？

**参考回答：**

项目 Snapshot 保存 KV 数据、request records、状态机 apply index/term 和 Raft 成员信息。Apply index/term 标识快照代表的状态边界；成员信息用于恢复配置。捕获状态时在状态机锁下复制 KV、去重记录和 apply 位置，避免并发 apply 造成数据内容与索引不匹配。

随后持久化 Snapshot，并按其 index 裁剪旧 WAL。安装端先接收并发布完整快照，再恢复状态机并安装 Raft 快照边界，之后继续追赶后续日志。

### 34. 为什么先保存 Snapshot 再裁剪 WAL？中间崩溃怎样恢复？

**参考回答：**

Snapshot 是旧日志前缀的替代恢复状态，必须先可靠持久化，才能删除被它覆盖的 WAL。若 Snapshot 已发布但 WAL 尚未裁剪时崩溃，恢复时依据 Snapshot index 丢弃 `index <= snapshot_index` 的冗余 WAL，再处理后续连续日志。

反过来先删 WAL、再写 Snapshot，如果在 Snapshot 可靠落盘前崩溃，就可能同时失去旧状态和恢复日志。项目还用临时文件、原子替换和目录 fsync 保护文件发布边界。

### 35. Snapshot 安装中网络断开怎么处理？怎样避免发布不完整快照？

**参考回答：**

安装时按 offset 分块写入临时 Snapshot 文件；接收方检查来源、term、snapshot index/term 和期望 offset 是否匹配，offset 连续后追加并 fsync。只有收到完整数据后才通过 rename 发布正式 Snapshot，之后加载其元数据与内容并恢复状态机。

中断时临时文件不应被当作可用快照发布。重试应遵守会话和 offset 协议；若 offset 不匹配，应返回错误并由传输流程重新续传或重新开始。测试要覆盖重复块、缺块、错误 offset、中断和最终发布边界。

### 36. 如何证明功能正确？举出能暴露问题的测试。

**参考回答：**

我会按协议层、组件层和端到端层设计测试，并把测试结果和覆盖范围说准确：

- **旧 Leader 恢复**：三节点中隔离旧 Leader，让多数派选出新 Leader并提交写，再恢复旧节点；验证旧节点退位、已提交日志不丢、落后后缀被修复，并验证 PreVote 减少无效 term 干扰。
- **成员变更**：增加 Learner，确认它追上 Leader 后才升为 Voter；在追赶中断、Leader 切换和移除成员时检查 quorum、成员配置与路由状态。
- **重复请求**：同一 request_id 和相同 payload 重试不重复执行；同 ID 不同 payload 被拒绝；重启或 Snapshot 恢复后仍能识别原请求。
- **WAL 尾部损坏**：注入部分记录、解码错误和 index gap；验证保留有效前缀、标记恢复状态，并避免把不确定的已提交数据静默丢弃。
- **Snapshot 安装中断**：中途断开、重复 chunk、offset 错误后重试；确认临时文件不会提前成为正式状态，完成后状态机和日志边界一致。

项目已有 Raft Cluster、PersistEngine、Replica、状态机和 E2E 用例；回答时应说明某个用例实际覆盖了什么，以及是否在当前环境重新运行，不能把“仓库有测试”说成“所有故障场景刚刚验证通过”。
